## 一、需求背景

### 1.1 现状问题

当前世界观只有"诛仙库"一本书的内容：

```
世界观百科
  └── 诛仙库（bookId=1）
        ├── 人物
        ├── 门派
        ├── 地点
        ├── 功法
        └── ...
```

**问题**：
1. **只有一本书** —— 想写别的故事（非诛仙）没有世界观基础
2. **诛仙库不能改** —— 诛仙库是公共数据，用户不能直接修改
3. **想基于诛仙创作新书很麻烦** —— 要一个一个手动复制实体到自定义模块
4. **自定义实体分散** —— 自定义人物在"众生百态"、功法在"道法自然"、法宝在"铸器天工"，跟世界观是分开的

### 1.2 需求目标

| 目标 | 说明 |
|------|------|
| **多书籍支持** | 世界观可以有很多本书，每本书有独立的实体数据 |
| **批量引入** | 可以从诛仙库（或其他书）批量选择实体，引入到新书中 |
| **引入后可编辑** | 引入的数据属于新书，用户可以自由修改 |
| **统一管理** | 一本书的所有实体（人物/门派/功法等）在一个地方统一管理 |

### 1.3 核心价值

```
之前：诛仙库（只读） + 自定义（分散在3个模块）
  ↓
之后：多本书（每本书独立、可编辑、可从其他书引入）
```

## 二、现状分析

### 2.1 当前架构

**双库架构**：

| 数据库 | 用途 | 表数量 | 可编辑 |
|--------|------|--------|--------|
| novel_db（诛仙库） | 诛仙小说结构化数据 | 18 张 | ❌ 基本只读 |
| novel_studio（创作库） | 用户创作数据 | 40+ 张 | ✅ 可编辑 |

**当前 bookId 用法**：
- 世界观百科有 BookSwitcher（书籍切换）
- 但实际上可能只有 bookId=1（诛仙）
- 自定义实体用负数 ID，存在创作库

**自定义实体分散**：
| 实体类型 | 所在模块 | 存储位置 |
|----------|----------|----------|
| 自定义人物 | 众生百态 | 创作库 |
| 自定义功法 | 道法自然 | 创作库 |
| 自定义法宝 | 铸器天工 | 创作库 |
| 诛仙人物/功法/... | 世界观 | 诛仙库 |

### 2.2 当前问题

1. **体验割裂** —— 想看全部人物？要在"世界观"和"众生百态"之间来回切
2. **不能批量复制** —— 想把诛仙的 10 个人物放到自己的书里？要手动一个个建
3. **书籍概念弱** —— 虽然有 bookId，但用户感知不到"多本书"
4. **引入后关系断裂** —— 手动复制的话，人物和门派的关系就没了

## 三、需求详情

### 3.1 功能定位

**一句话**：世界观支持多本书，每本书有独立的实体数据；可以从诛仙库（或其他书）批量选择实体，一键引入到新书中，引入后的数据属于新书，可自由编辑。

### 3.2 核心功能

#### 3.2.1 书籍管理

| 功能 | 说明 |
|------|------|
| 书籍列表 | 展示所有书籍（诛仙库 + 用户创建的书） |
| 创建新书 | 新建一本书，初始为空 |
| 从模板创建 | 基于诛仙库（或其他书）创建，可选引入哪些实体 |
| 书籍信息编辑 | 修改书名、简介、封面等 |
| 删除书籍 | 删除整本书（带确认） |

#### 3.2.2 批量引入

| 功能 | 说明 |
|------|------|
| 选择源书籍 | 从哪本书引入（默认诛仙库） |
| 选择实体类型 | 引入哪些类型（人物/门派/地点/功法...） |
| 批量选择实体 | 列表 + 搜索 + 筛选 + 全选 |
| 预览引入内容 | 确认要引入的实体列表 |
| 执行引入 | 批量复制到目标书籍 |
| 引入结果 | 成功/失败数量 + 详情 |

#### 3.2.3 引入后的处理

| 功能 | 说明 |
|------|------|
| 数据归属 | 引入的数据属于目标书籍，存在创作库 |
| 可编辑 | 引入后可以自由修改、删除 |
| 关系保留 | 实体之间的关系（人物→门派、功法→门派等）一起引入 |
| ID 转换 | 原 ID → 新 ID（负数 ID 规则） |
| 来源标记 | 标记"来源：诛仙库"，方便追溯 |

### 3.3 引入范围

**支持引入的实体类型**：

| 类型 | 说明 | 关系处理 |
|------|------|----------|
| 人物 | 角色设定 | 保留所属门派、所在地等关联 |
| 门派 | 宗门设定 | 保留掌门、所在地等关联 |
| 地点 | 地理设定 | 保留所属区域等关联 |
| 功法 | 功法设定 | 保留所属门派、招式等关联 |
| 法宝 | 法宝设定 | 保留持有者等关联 |
| 妖兽 | 妖兽设定 | — |
| 丹药灵材 | 丹药和灵材 | — |
| 日常信物 | 日常物品和信物 | — |

**支持引入的关联数据**：
- 人物关系
- 功法招式
- 实体之间的关联（人物→门派、人物→所在地等）

## 五、数据模型设计

### 5.1 书籍表

新增 `book` 表（如果还没有的话）：

| 字段 | 类型 | 说明 |
|------|------|------|
| id | int | 书籍 ID |
| name | varchar | 书籍名称 |
| description | text | 书籍简介 |
| source_type | enum | 来源类型：system（系统内置）/ user（用户创建） |
| source_book_id | int | 来源书籍 ID（如果是从其他书引入的） |
| entity_count | jsonb | 各类实体数量统计 |
| created_at | timestamp | 创建时间 |
| updated_at | timestamp | 更新时间 |

**初始数据**：
- bookId=1，诛仙库，source_type=system

### 5.2 实体存储方案

**方案 A：全部存创作库（推荐）**

所有书籍的所有实体都存在创作库（novel_studio），用 book_id 区分。

```
character 表
  ├── book_id=1（诛仙库数据，初始化时导入）
  ├── book_id=2（用户的第一本书）
  └── book_id=3（用户的第二本书）
```

**优点**：
- 统一管理，查询简单
- 所有书的数据结构一致
- 方便跨书操作

**缺点**：
- 诛仙库数据要从 novel_db 迁移到 novel_studio
- 数据量变大

**方案 B：诛仙库不动，用户书存创作库**

诛仙库还在 novel_db，用户创建的书存在 novel_studio。

**优点**：
- 不用动诛仙库
- 数据隔离好

**缺点**：
- 查询要跨库，复杂
- 批量引入要跨库复制
- 统一展示麻烦

**建议**：方案 A，全部存创作库，诛仙库数据作为初始数据导入。一次麻烦，后面都方便。

### 5.3 引入记录表

新增 `entity_import_log` 表，记录每次引入操作：

| 字段 | 类型 | 说明 |
|------|------|------|
| id | int | 主键 |
| source_book_id | int | 源书籍 ID |
| target_book_id | int | 目标书籍 ID |
| entity_type | varchar | 实体类型 |
| source_entity_id | int | 源实体 ID |
| target_entity_id | int | 目标实体 ID |
| status | enum | success/failed |
| error_message | text | 失败原因 |
| created_at | timestamp | 引入时间 |

### 5.4 实体来源标记

每个实体表增加字段：

| 字段 | 类型 | 说明 |
|------|------|------|
| source_type | enum | 来源：original（原创）/ imported（引入） |
| source_book_id | int | 来源书籍 ID |
| source_entity_id | int | 源实体 ID |
| is_modified | boolean | 是否被修改过 |

## 六、技术实现思路

### 6.1 批量引入流程

```
1. 选择源书籍和目标书籍
2. 选择要引入的实体列表
3. 按依赖顺序引入（先引入门派，再引入人物，因为人物关联门派）
4. 每个实体：
   a. 从源书籍读取实体数据
   b. 生成新 ID（负数 ID 规则）
   c. 写入目标书籍
   d. 记录引入日志
5. 处理关联关系：
   a. 人物→门派：门派 ID 替换为新 ID
   b. 功法→门派：门派 ID 替换为新 ID
   c. 人物关系：双方 ID 都替换
   d. 等等...
6. 返回引入结果
```

### 6.2 依赖顺序

引入时要注意依赖顺序，先引入被依赖的，再引入依赖的：

```
引入顺序：
  1. 地点（最基础，不依赖其他）
  2. 门派（依赖地点）
  3. 人物（依赖门派、地点）
  4. 功法（依赖门派、人物）
  5. 法宝（依赖人物）
  6. 妖兽、丹药、信物（独立）
```

### 6.3 ID 转换规则

沿用现有的负数 ID 设计：

```
源实体 ID（正数） → 目标实体 ID（负数）
  例：诛仙人物 ID=123 → 新书人物 ID=-123
```

但要注意：
- 不同书的实体 ID 不能冲突
- 可以用 book_id + 原 ID 生成唯一新 ID
- 或者每本书有自己的 ID 序列

### 6.4 关系处理

**关系映射表**：
引入前先建立"源 ID → 新 ID"的映射表，然后所有关联字段都用映射表替换。

```
映射表示例：
  人物：
    123 → -1001
    456 → -1002
  门派：
    10 → -2001
  
人物"张小凡"(ID=123) 的 faction_id=10
  → 引入后 faction_id = 映射表[10] = -2001
```

### 6.5 性能考虑

**批量引入的性能优化**：
- 用批量 INSERT，不是一条条插
- 事务包裹，失败回滚
- 大数量时分批引入（如每批 100 个）
- 异步处理，前端显示进度

## 七、优先级与排期建议

### 7.1 优先级评估

| 需求点 | 用户价值 | 实现难度 | 优先级 |
|--------|----------|----------|--------|
| 多书籍基础框架 | ⭐⭐⭐⭐ 基础能力 | ⭐⭐⭐ 中等 | **P0** |
| 从诛仙库批量引入 | ⭐⭐⭐⭐⭐ 核心需求 | ⭐⭐⭐ 中等 | **P0** |
| 书籍管理 UI | ⭐⭐⭐ 体验优化 | ⭐⭐ 简单 | **P1** |
| 引入关系保留 | ⭐⭐⭐⭐ 重要 | ⭐⭐⭐ 中等 | **P1** |
| 跨书引用/同步 | ⭐⭐ 高级功能 | ⭐⭐⭐⭐ 难 | **P2** |

### 7.2 与其他需求的关系

| 需求 | 关系 |
|------|------|
| 需求一（智能匹配生成） | 独立，但引入后的实体可以用智能匹配生成新的 |
| 需求二（一键批量生成） | 互补：批量生成是从文本创建，批量引入是从其他书复制 |
| 自定义工坊（众生百态等） | **可以合并**：引入后自定义实体和引入实体统一在世界观里管理 |

### 7.3 排期建议

**第一阶段（2-3 周）：基础框架 + 批量引入 MVP**
- 多书籍数据模型改造
- 书籍管理基础 UI
- 从诛仙库批量引入人物+门派
- 基础关系保留

**第二阶段（1-2 周）：完善**
- 支持全部 8 类实体引入
- 完善关系处理（人物关系、功法招式等）
- 引入进度展示
- 引入日志/历史

**第三阶段（长期）：高级功能**
- 跨书引用（不是复制，是引用源数据）
- 源数据更新同步
- 书籍模板市场
- 等等...

### 7.4 风险点

| 风险 | 影响 | 应对 |
|------|------|------|
| 数据迁移复杂 | 诛仙库数据搬到创作库工作量大 | 先做迁移脚本，充分测试 |
| ID 冲突 | 不同书的实体 ID 可能冲突 | 设计好 ID 生成规则 |
| 关系处理遗漏 | 有些关系没处理，引入后断了 | 梳理所有关系字段，逐个处理 |
| 性能问题 | 大批量引入慢 | 批量插入、异步处理、进度展示 |

## 八、对现有架构的影响

### 8.1 自定义工坊的去向

**问题**：有了多书籍世界观，"众生百态/铸器天工/道法自然"三个自定义模块怎么办？

**方案 A：合并到世界观（推荐）**
- 所有实体都在世界观里统一管理
- 众生百态/铸器天工/道法自然 变成世界观的快捷入口或特殊视图
- 优点：统一管理，体验好
- 缺点：改动大

**方案 B：保留独立模块**
- 三个自定义模块继续存在
- 世界观只管理"书籍"的实体
- 优点：改动小
- 缺点：还是分散，体验割裂

**建议**：长期来看方案 A 更好，但可以分步走——先做多书籍和批量引入，后面再考虑合并。

### 8.2 双库架构的变化

如果采用方案 A（全部存创作库）：

```
之前：
  novel_db（诛仙库，只读） + novel_studio（创作库，读写）

之后：
  novel_studio（所有书都在这里，用 book_id 区分）
  novel_db 可以保留作为原始数据源，也可以废弃
```

*文档完成。本需求与前两个需求（智能匹配生成、一键批量生成）共同构成"世界观内容生产"的三条路径：从其他书引入、从文本生成、手动配置。*
