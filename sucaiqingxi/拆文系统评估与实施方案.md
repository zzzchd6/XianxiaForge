## 0. TL;DR（30 秒看懂）

- **结论：做，但不要从头做。** 需求方案整体可行，且 `sucaiqingxi/` 已经把最难的底座（LLM 抽取管线 / 向量存储 / 去重 / GUI 后台任务 / 降本机制）铺好了，真正的新增量只有三块：① 章节边界切分；② 两张对标表 + 原文定位字段；③ 骨架/情节合并的纵切 Prompt。
- **定位修正**：现有工具做的是「横切」（从书中抽可跨书复用的剧情模式），需求做的是「纵切」（给一本书做结构化注解 = 这本书的 DNA 图谱）。两者互补，不重复；横切结果可直接作为纵切的应用层数据。
- **最大惊喜**：`Lorn.NovelWriteSkills-main/CommonSkills/` 下已有现成的拆文方法论 skill 资产（`通用-分析竞对作品` 四层深拆、`通用-蒸馏作品蓝本` 叙事架构 DNA/黄金三章、`通用-设计线索伏笔与回收台账` 伏笔台账/回收窗口）——**拆文 Prompt 方法论不用从零发明，可直接提炼为 LLM 拆解 Prompt 的规则来源**。
- **第一个必修的坑**：`extract_materials.py:128` 的清洗规则会**整行删除章节标题**（`第X章`），直接复用会导致章节边界丢失，必须新增独立章节切分函数。
- **成本红线**：四步拆解若按字面每章过 4 遍 LLM，200 万字整本成本不可接受。骨架+情节合并为一次调用、长篇拆解抽样跑通，是必须的降本设计。

## 3. 方案选型

### 3.1 存储：放弃"5 库"，用 1+1 张表（对标书 + 对标条目）

需求 §一 设计骨架库/冲突库/人物库/技巧库/钩子库 5 个独立知识库。**不采用**。理由：

- 5 张独立库表结构高度同构（都是"类型 + 内容 + 标签 + 向量"），拆分只会让检索要跨 5 张表 UNION，纯增复杂度；
- 学 oh-story 的 `对标/{书名}/` 目录哲学与现有 4 张素材表的对称风格，改为：

```sql
-- benchmark_book：对标书主表
CREATE TABLE IF NOT EXISTS benchmark_book (
  id              BIGSERIAL PRIMARY KEY,
  project_id      BIGINT REFERENCES creative_project(id) ON DELETE CASCADE, -- NULL=全局共享
  book_name       VARCHAR(200) NOT NULL,
  author          VARCHAR(100),
  platform        VARCHAR(50),            -- 起点/番茄/晋江...
  total_words     INT,                    -- 总字数
  source_path     VARCHAR(500),           -- 原文 TXT 路径（仅后台可见）
  analyze_status  VARCHAR(20) DEFAULT 'pending',  -- pending/running/done/failed
  summary         TEXT,                   -- 整书综述（书级 DNA 摘要）
  created_at      TIMESTAMP DEFAULT NOW()
);

-- benchmark_item：对标条目表（item_type 枚举区分，检索时 WHERE book_id=X AND item_type=...）
CREATE TABLE IF NOT EXISTS benchmark_item (
  id              BIGSERIAL PRIMARY KEY,
  book_id         BIGINT REFERENCES benchmark_book(id) ON DELETE CASCADE,
  item_type       VARCHAR(20) NOT NULL,   -- skeleton | plot_node | variable | long_form | style
  title           VARCHAR(200) NOT NULL,  -- 一句话概括
  content         TEXT NOT NULL,          -- 抽象化内容（骨架/节点/变量描述），参与向量化
  chapter_idx     INT,                    -- ★ 原文定位：所属章节序号
  char_start      INT,                    -- ★ 原文定位：章内字符偏移起点
  char_end        INT,                    -- ★ 原文定位：章内字符偏移终点
  qi_ratio        NUMERIC(5,2),           -- ★ 起承转合比例落列（可直接 SQL 过滤"节奏快的书"）
  cheng_ratio     NUMERIC(5,2),
  zhuan_ratio     NUMERIC(5,2),
  he_ratio        NUMERIC(5,2),
  emotion_curve   NUMERIC[],              -- ★ 情绪曲线（归一化后），两书曲线可直接点积比较
  ext             JSONB,                  -- 扩展细节（key_nodes/推拉模式/钩子清单等）
  tags            TEXT[] DEFAULT '{}',
  quality_score   INT DEFAULT 0,
  source_snippet  VARCHAR(300),           -- 原文片段（仅后台可见，禁止注入写作上下文）
  embedding       VECTOR(512),            -- content 的 512 维 bge 向量
  is_deleted      BOOLEAN NOT NULL DEFAULT FALSE,
  created_at      TIMESTAMP DEFAULT NOW()
);
```

**关键点**：
- `chapter_idx + char_start + char_end` 是工作台原文高亮（§4 界面）和参考借鉴对比视图（§5.3）的**数据基础**，没有它拆解结果与原文之间就是断的——这是对需求文档的**必要补充字段**；
- 起承转合比例落 4 个数值列（可 SQL 过滤）、情绪曲线落 `NUMERIC[]`（可曲线相似度计算）、扩展细节才进 JSONB——**不要什么都塞大 JSONB**，这是二期需求文档已经验证过的教训；
- `item_type` 枚举替代 5 库：`WHERE book_id=X AND item_type='plot_node'` 就是"情节库"，`item_type='variable'` 就是"骨架/变量库"。

### 3.2 拆解引擎：四步 = 2 次 LLM 调用（省 ~50% token）

| 需求步骤 | 合并策略 | 说明 |
|----------|----------|------|
| 骨架级 + 情节级 | **合并 1 次调用** | 共享同一输入、信息高度重叠（LLM 画情绪曲线必然已识别节点）。现有 `extract_materials.py:216` 已验证"单次合并抽多类"模式 + JSON 容错，直接照搬 |
| 变量级 | 独立 1 次调用 | 依赖骨架抽象结果，需上一步输出 |
| 长篇级 | 独立 1 次调用（抽样） | 单元划分/伏笔台账成本最高，先抽样 |

减法测试（§变量级 Step 1）**不做全量逐段 LLM**：先零 token 启发式（段落长度/实体密度/节点功能类型）预筛候选核心支点，**只对情节级标记的"推进型/爆发型"节点做减法测试**——这是 `should_skip_chunk` 预筛思想（`extract_materials.py:197-208`）的延伸。

### 3.3 方法论来源：提炼 Lorn 资产，不发明轮子

| 拆解维度 | 方法论来源（Lorn CommonSkills） | 提炼方式 |
|----------|--------------------------------|----------|
| 骨架级（起承转合/情绪曲线） | `通用-蒸馏作品蓝本/references/作品蓝本模板格式定义.md`、`结构DNA符合度审计.md` | 翻译成 Prompt 中的"结构分段规则 + 情绪强度打分标准" |
| 情节级（3 问模型） | `通用-分析竞对作品/references/拆书方法论_场景级拆解技法.md` | 翻译成节点切分规则 + Why Now/How to Pay 提问模板 |
| 长篇级伏笔台账 | `通用-设计线索伏笔与回收台账/references/台账字段与分层规则.md`、`伏笔类型分类与回收周期.md`、`超长篇伏笔台账与回收节奏.md` | 直接翻译成 `benchmark_item` JSONB 的伏笔台账结构 + 埋/收配对规则 |
| 变量级（骨架抽象） | `通用-蒸馏作品蓝本/references/仿写内核提取与骨架模型.md`、`套路指纹分类体系.md` | 翻译成 9 变量提取规则 + 通用骨架判定标准 |

### 3.4 与二期 RAG 的关系（不重复建设）

- 拆文产物的"参考借鉴"（§5）与"灵感生成"（§8）**本质上就是 RAG 检索**，与二期 `plot-material-retriever.ts` 是同一套机制；
- 落地顺序：**先落地二期 RAG（4 类素材 + 文风 + 领域知识）→ 再把 `benchmark_item` 表加入检索数据源**，复用同一检索器，不另起炉灶；
- 高质量拆文节点可**回流 4 类素材表**（横切复用）：拆出的高质量冲突 → `plot_material_highlight`，好伏笔 → `plot_material_foreshadow`，复用现有 ETL 的去重/质量门槛逻辑。

### 3.5 质量检测独立成模块（不绑死拆文系统）

需求把质量检测列为拆文四大应用之一。**修正为独立模块**：输入 = 标准配置（起承转合比例 / 情绪密度 / 钩子频率，来自 `benchmark_book` 聚合或人工预设），输出 = 检测报告。拆文系统只负责产出"标准"，不负责执行检测——这样平台签约标准（Lorn 有 `通用-平台签约评估框架`）也能作为标准来源，不锁死单一数据源。

### 3.6 跨题材映射表（§6.3）数据库驱动，不硬编码

"都市→仙侠"硬编码映射表会随题材组合爆炸（45 种组合）。改用现有 `plot_domain_knowledge` 表（5 类知识）——把"角色类型→跨题材对应关系"作为一类领域知识入库，变量替换时 RAG 动态检索。

## 4. 否决项与理由

> 本需求整体前提成立，无硬否决项。以下 2 项是"方向对但实现方式需修正"的否决式裁定。

### 否决 1：知识库 5 库独立存储
- 文档原文：§一「骨架库 │ 冲突库 │ 人物库 │ 技巧库 │ 钩子库」
- 否决理由：5 张同构表让检索跨表 UNION、维护翻 5 倍。基于核查证据——现有 `ddl-plot-material.sql:24-41` 的 4 张素材表已是"对称表 + item_type 概念"的成熟模式，`item_type` 枚举一张表即可表达全部 5 库语义（`ddl-plot-material.sql` 已验证 4 张对称表可行，但那是横切分表，纵切应按书聚合）。
- 替代建议：`benchmark_book` + `benchmark_item`（§3.1），`item_type` 枚举 skeleton/plot_node/variable/long_form/style。

### 否决 2：减法测试逐段全量 LLM
- 文档原文：§3.3 Step 1「逐段问'删掉这段，故事逻辑还通吗'」
- 否决理由：200 万字整本逐段过 LLM 成本不可接受；且减法测试是"逻辑判断"，40% 自动 + 60% 人工的设计本身就承认 LLM 做不好。基于核查证据——`extract_materials.py:77-84` 的 MAX_CHUNKS 限量说明作者自己也认同全量不可行。
- 替代建议：零 token 启发式预筛 + 只对"推进型/爆发型"节点做减法测试（§3.2）。
